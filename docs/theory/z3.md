## Results at a glance

The main result is Theorem 1: if z3 answers `unsat` only for unsatisfiable queries, the
prover takes each answer for the check that asked it, the build returns `T_β(M, σ)` at the run's bound (claim [I1](./claims.md#0-the-build)), and the encoding is faithful in the sense of [Faithfulness](#faithfulness-of-the-encoding), then
`proved: R` implies that `R` holds in every reachable state of `T_{β'}(M, σ)` for every bound
`β'` in the proof's scope `Sc(M, β)` (Definition 3): every slot count per entity at which the
model builds as at the run's bound, and every Int top `m'` at least the largest Int literal
the model states, except that `m'` may not exceed the run's `m` when the model has a
`.when`-guarded `present` write to a nullable Int column (P43), nor be 255 when the model has
a nullable Int column, unless `m' = m` (P40). `σ` is the run's scope (D24), not the whole model (P4). At the
pinned commit, then, the printed clause "for any number of rows and any Int value" is false for
a model with the P43 construct: a rule can print `proved` at `m = 5` and have a BFS
counterexample at `m = 7` ([Reproductions](#reproductions)).

What carries the theorem, and how strongly each part is supported:

| Part | Support |
|---|---|

| The printed text means the `Expr` it was built from (H2) | typed builder and its unit tests; assumed beyond them |
| Each answer is read for the check that asked it (H4) | assumed for z3's output protocol; the reader fails closed on any other line (`Z3::exec`, `Solver::check_sat`); no test drives the reader |
| The kept set is inductive relative to the encoding (Proposition 4) | proof from the code (Houdini loop, step pruning) |
| Step pruning (`breaks`) is sound (Lemma F5) | proof from the code |

| The definition is uniform in the bound (Lemma U₀) | immediate from D1 to D12, which read `β` at a few named places ([semantics.md](./semantics.md#remarks-on-the-definitions)) |
| The build returns `T_β(M, σ)` at the run's bound (claim [I1](./claims.md#0-the-build)) | not argued as a whole; the corpus headers, and the planned reference interpreter of P26 on its subset. P40 was a departure, fixed in #470 |

## Notation

<!-- constrained-by ./semantics.md#notation -->

The following symbols are new here. Everything else is D1 to D24.

- `β = (n, m)` is the run's bound (D1). The prover receives `T`, the system
  `TransitionSystem::build(M, β, σ)` returns. `T` is `T_β(M, σ)` (D13, D24) when claim I1
  holds at `β`. `T_{β'}` always means the system D13 defines at `β'`, never a build output.
- `Enc` is the encoding of `T` in SMT-LIB 2 built by `core/prove/encode.rs::Enc`. It
  consists of:
  - `Decl`: `Enc::declarations`, the sorts, the pre-state functions, and the domain facts;
  - `Init`: `Enc::initial`, the initial-state facts;
  - `Step_a`: `Enc::step(a)`, for each action `a` of `T`, the step relation, with its
    parameters `p0 … p_{r-1}` and fresh constants `c0 …` as free constants;
  - `⟦φ⟧^F`: `Enc::holds(φ, F)`, a state formula closed over its binders, read in frame
    `F ∈ {Pre, Post}`; `Viol(φ, F)`: `Enc::violation(φ, F)`, the assertion that some rows
    break it.
- A *candidate* is a formula `ψ` the prover may keep (`core/prove/mod.rs::Candidate`): a rule
  of `T` (D16), a built-in lemma, a mined lemma, or a clause from a CTI.
- `reads(ψ)` is the set of variables `ψ` reads: `TransitionSystem::pred_reads` of its body plus
  the existence variable of each binder. `writes(a)` is `TransitionSystem::action_writes(a)`.
- A set `K` of candidates is *inductive relative to `Enc`* when (initiation)
  `Decl ∧ Init ∧ Viol(ψ, Pre)` is unsatisfiable for each `ψ ∈ K`, and (consecution)
  `Decl ∧ Step_a ∧ ⋀_{χ∈K} ⟦χ⟧^Pre ∧ Viol(ψ, Post)` is unsatisfiable for each action `a` and
  each `ψ ∈ K`.
- For a state `s` of some `T_{β'}`, `𝔄(s)` is the structure of
  [Faithfulness](#faithfulness-of-the-encoding) that reads `s` as an interpretation of the
  signature of `Enc`.

## The encoding

<!-- derived-from ../formal-verification.md#proofs-for-any-number-of-rows -->

### Sorts and the term builder

`core/prove/smt.rs` builds SMT-LIB terms as data. An `Expr` carries its sort (`Sort::Bool`,
`Sort::Int`, or `Sort::Ent(e)`), each constructor checks the sorts it takes, and one printer
writes every parenthesis (#426, #431). A sort mismatch panics in a debug build; in a release
build z3 rejects the text, `Z3::exec` turns the `(error ...)` line into a `SolverError`, and the
run fails without a verdict (`cli/src/prove.rs::run_proof` maps it to `z3 failed`). So a printer
bug that produces ill-sorted text cannot read as `proved`; it can only stop the run. A printer
bug that produces well-sorted text meaning something other than the `Expr` is not caught this
way; that is hypothesis H2 of Theorem 1.

`core/prove/solver.rs::Z3` keeps one `z3 -in -smt2` process per solver for the whole proof and
reads its answers up to an echoed marker. `Solver::check_sat` sets `:rlimit` for one check and
resets it to 0 after; `sat`, `unsat`, and `unknown`/`timeout` are the three answers (`Sat`), and
anything else is a `SolverError`.

### The answer reader

That an answer is taken for the check that asked it is hypothesis H4 of
Theorem 1. `Z3::exec` writes a batch of commands followed by `(echo "@@rdra-ish-done@@")`
(`MARK`), then reads stdout line by line: it returns the lines before the first line equal to
`MARK`, returns a `SolverError` at the first line that starts with `(error`, and returns one
when stdout closes. `Solver::check_sat` sends `(set-option :rlimit k) (check-sat)
(set-option :rlimit 0)` as one batch and reads only the first line `exec` returns. So H4 holds
when z3 processes a batch's commands in order, prints the marker once after them, prints
nothing for `set-option`, `push`, `pop`, `assert`, `declare-*`, and `define-fun` (`:print-success`
is off by default, and the prover never sets it), and prints no line equal to the marker;
z3's stderr is discarded (`Stdio::null`). Two facts of the code keep a misread from turning into
`proved`. A first line other than the four answers is a `SolverError`, and every caller
propagates a `SolverError` with `?` up to `cli/src/prove.rs::run_proof`, which fails the run
with `z3 failed`; so a session is never used after an error, and `exec`'s early return at an
`(error` line, which leaves the rest of the batch unread, cannot shift later answers by one
batch. What the code cannot see is a well-formed answer that belongs to another check, which
needs z3 to break the protocol above. No unit test drives `exec` or `check_sat` (the tests of
`solver.rs` parse `get-value` output only); every proof test exercises them against z3 5.1.0.

### How rows of unbounded count are represented

Each entity `E` becomes an uninterpreted sort `E<i>` (`Command::DeclareSort`). The sort's
elements are the rows; nothing bounds how many there are, and a model of `Enc` may have any
finite or infinite number of them. Two named elements exist in every sort:

- `nil<i>`, the value of an unlinked optional key; it is never a row (`Decl` asserts its
  existence is `absent`, so no quantifier over present rows reaches it);
- `zero<i>`, the slot a non-optional key holds at its base value (slot 0 in `T`), distinct
  from `nil<i>`.

Every row variable `v` of `E` (D2) becomes a unary function `v<k> : E<i> → Int` holding the
domain index (`Value`) of `v`, or `E<i> → E<j>` when `v` is a key into `E<j>`
(`Enc::func`, `Enc::var_sort`). The successor reads `v<k>_n`. `now` is an `Int` constant, `now`
and `now_n`. Marks (`Run`, `Raised`) and driven propositions are row functions like columns.

### Domain facts (`Decl`)

`Enc::declarations` asserts, for every row `x`:

- a finite-domain variable lies in `0 … size-1`, with `size = Domain::size` (Enum, Bool,
  nullable variants, existence, marks; none of these sizes depends on `β`);
- an Int-typed variable (`Domain::is_numeric`: Int, Money, Decimal, Date, DateTime, nullable
  or not) is `≥ 0`, with no top (`Enc::in_domain`);
- a non-optional key is never `nil`;
- `now ≥ 0`; `nil<i>` is absent.

The facts are asserted for the pre-state only. The post-state functions are defined
(`define-fun`) from pre-state terms, literals, and fresh constants that are themselves
constrained to the domain, so they stay in the domain by construction.

### Initial states (`Init`)

`Enc::initial` asserts, for every variable and every row, the start value of D4: the base
value (D3) for a created entity; for a pre-existing entity, `present` for existence and, per
`Start`, the base value, any value (`Start::Any`), or a key that is not `nil` together with
injectivity of the key function over non-`nil` rows (`Start::Identity`). The `nil` row is
pinned to the base value of every variable in every case (`ite(x = nil, base, start)`), which
Definition 1's reading of `⋆` satisfies.
`now = 0`. A base value the encoding cannot state (a key at a fixed slot other than 0) makes
`Init` `Unsupported`; then every candidate falls as `Unknown` and nothing is proved.

### Steps (`Step_a`)

`Enc::step` builds one step relation per action, in the order of `explore/moves.rs::
TransitionSystem::each_successor`:

1. **Parameters.** Each parameter is a fresh constant other than `nil`. `New` asserts that the
   row is absent: *any* absent row, where `T` takes the lowest absent slot (D7). `Existing`,
   `Parent`, and `Triggered` assert `present`; `Earlier` asserts nothing (its run-mark guard
   selects it, as in `T`).
2. **Effects, in effect order.** `Create` sets existence to `present`; `Assign` of a literal
   or of a parameter's row sets the variable on that row; a `Transition` whose current value
   has exactly one target sets it at once, conditioned on the current value. These are the
   same three in-order updates `each_successor` makes.
3. **Deletes**, after every other effect: the deleted row's columns return to base and its
   existence becomes `deleted`; keys and marks are kept (D8, D10), as in `each_successor`.
4. **Forks**, after deletes: a `Transition` with several targets for some current value and
   every `Choose` become a fresh constant constrained to the listed values, applied last, in
   effect order, and skipped on a deleted row, as `each_successor` drops choices on deleted
   rows.
5. **Guards.** Every guard of `a` is asserted on the pre-state, with `At::Next` reading the
   successor, except `GuardWhy::Clock` (the `now < m` guard of `Tick`), which is dropped.
   Quantifiers and `now` inside a guard read the pre-state in both `Enc` and `expr.rs::eval`
   (`eval` reads `env.next` only for an `At::Next` slot).

`Tick` sets `now_n = now + 1`. Every variable no effect writes keeps its pre-state function
(`cur` returns `v<k>(x)`), so the post-state differs from the pre-state only on variables in
`writes(a)`; this is Lemma F5.

### Predicates

`Enc::pred` follows `Pred` node by node. `Forall`/`Exists` over `E` quantify over rows with
existence `present`, as `expr.rs::quantify` ranges over present slots. `Count{E, φ, op, k}` is
built from `at_least(k)`: `k` pairwise distinct witnesses, each present and satisfying `φ`. That
is exact, in either polarity, so `≥ k`, `> k`, `≤ k`, `< k`, `== k`, `!= k` are exact as long as
every `at_least(j)` they need has `j ≤ COUNT_WITNESSES = 8`; past that the formula is
`Unsupported`. So `≥ 8` and `< 8` are stated, `> 8`, `≤ 8`, `== 8`, and `!= 8` are not
(`.at_most(7, ..)` is the largest `at_most`, `.exactly(7, ..)` the largest `exactly`).

`Enc::compare` mirrors `expr.rs::compare` (D5) case by case:

| Case | `expr.rs::compare` | `Enc::compare` |
|---|---|---|
| key against a row (`Term::Index`) | linked iff the key names the slot; only `==`, `!=` | the key function equals the row; only `==`, `!=`; a non-key against a row is `Unsupported` |
| either side numeric | `Domain::number` (nullable Int: index 0 is null, `i` is `i-1`); null `==` only null, never ordered | the pair (is null, number), same truth table |
| keys and literals | raw indices: an optional key's 0 is null, a non-optional key's 0 is slot 0 | `nil` and `zero`; any other fixed slot, a key against a key of another shape, and an ordering of rows are `Unsupported` |
| other domain indices | raw index order | raw index order |

On every case both implement, the two agree by inspection; this is the reading of P3's
"`Enc::compare` re-implements `expr.rs::compare`". The cases `Enc::compare` rejects only make a
formula `Unsupported`, which the next section turns into a widening or an `out of scope`.

### What is folded, what is widened, and what is unsupported

Three different mechanisms change what a predicate or step says, and they have different
consequences.

**Folding, in the builder.** `core/build/preds/atoms.rs::lists_whole_domain` replaces an `in`
set that lists every value of an Enum, Bool, nullable-or-present, or existence variable by
`true` (and `not in` by `false`). These domains do not depend on `β`, so the fold is exact in
`T_{β'}` for every `β'` and in `Enc`. An Int, nullable Int, or key domain is never folded,
because its values are as many as `β` says (#425, fixed in #429). Before #429 a rule
`n not in (null, 0, 1, 2, 3, 4, 5)` was folded at `m = 5` and printed `proved`, while BFS at
`m = 7` refuted it; the corpus cases `z3_int_listing_whole_range`, `z3_int_listing_guard`, and
`z3_int_listing_past_the_top` hold the fix in place under `proof_equivalence`'s wider-Int axis.

**Widening, in the encoder.** Three constructs are encoded with more behaviors than `T_β` has:

- a `New` parameter takes any absent row;
- `Tick` has no guard, and Int-typed variables and `now` have no top;
- a `Choose` over an Int-typed variable whose listed values are every index from 1 at `β`
  (with or without 0) is encoded as `c ≥ 1` (or `c ≥ 0`), any number (`Enc::one_of`). That is
  how the builder writes `sets(.., col == present)` on a nullable Int (`EffectRhs::AnyNonNull`
  lists `1 … size-1`), a copy, and an unconstrained choice (`(0..size)`). The widening covers
  the effect only. When the write carries `.when(C)`, `build/transitions.rs::arm_guards` also
  adds a guard `⋁_v (next.n = v ∧ C)` over the same list, and `Enc::step` asserts that guard
  as built, so the encoded step can still write only the values listed at `β` (P43, see
  [Uniformity in the bound](#uniformity-in-the-bound)).

**`Unsupported`.** A construct the encoder cannot state is handled by where it occurs:

- in a guard: the guard is dropped (`loose`, printed as `note: not encoded …`); dropping a
  conjunct of a step's guard only adds steps;
- in a write: the written value is a fresh constant constrained only to the domain
  (`Enc::havoc`); this includes the old and the true new value, so it only adds steps;
- in a candidate: a rule is `out of scope` and is not tried; a lemma is silently dropped.

No rule is ever approximated: `Unsupported` in a rule's body or binders yields
`Verdict::OutOfScope`, never a weaker formula (B7).

### Uniformity in the bound

<!-- constrained-by ./semantics.md#remarks-on-the-definitions -->

The encoder reads only `T`, the build's output at `β`. Theorem 1 is about the systems
`T_{β'}(M, σ)` that D13 defines at other bounds `β'`. So it needs two things. First, `T` is
`T_β(M, σ)`: this is claim I1 at `β`. Second, `T_{β'}` differs from `T_β` only in ways the
encoding already covers.

**Lemma U₀ (uniformity of the definition).** Let `β' = (n', m')` satisfy D1, with every Int
literal of the model at most `m'`. Then `T_{β'}(M, σ)` has the same entities, variables, and
actions as `T_β(M, σ)`, with the same parameters, guards, and effects, and its rules have the
same binders and bodies. The exceptions are the places where D1 to D12 read the bound:

- the domains of D2: number columns have `[m'+1]` (or `[m'+1]⊥`), keys `[n'_P]` (plus `⊥`);
- D4's Identity starts and D7's slots, through `n'`;
- D8's `present` written to a nullable number column, a choice over `[m'+1]`, together with
  the `.when` bodies that filter that choice;
- D12's `Tick` guard, `now < m'`.

*Proof.* Read D1 to D12. ∎

Lemma U₀ is about the definition. Lemma U below is about the build: it says that the build
reads the bound only where the definition does. That makes it evidence for the uniformity
half of claim I1. Each of its items 1 to 4 is a case of Lemma U₀, stated in the build's vocabulary.
Item 4 is the `.when`-filtered `present` choice. The encoding does not widen it, which is
P43, a fault of the encoding across bounds and not of the build at `β`. Item 5 is not a
difference between defined systems: at `m' = 255` the build wrote `⊥` where D8 writes 255.
That was a departure from the definition, a failure of I1 (P40), and #470 fixed it.

**Lemma U (uniformity of the build).** Let `β' = (n', m')` be such that `TransitionSystem::build(M, β', σ)`
reports no error, and let every Int literal the model states be at most `m'`. Then the system
that call returns has the same entities, variables, and actions as `T`, with the same parameters, guards, and
effects, and its rules have the same binders and bodies, except that:

1. each `Domain::Int`/`NullableInt` has `m'+1` (or `m'+2`) values, and each key domain has
   `n'_P` (`+1`) values;
2. each `Choose` the builder fills with every value of an Int-typed domain lists the values at
   `m'` instead of `m`;
3. the `Tick` guard compares `now` with `m'`;
4. (P43) an `ArmCondition` guard that `build/transitions.rs::arm_guards` builds from such a
   `Choose` lists the values at `m'` instead of `m`. `arm_guards` builds a guard only from a
   `Choose` with conditions, and of the five places in `core/build` that push a `Choose`, only
   `build/sets.rs::guarded_set` attaches conditions to a list that `Domain::size` fills: a
   `.when`-guarded `sets(UC, E.n == present)` on a nullable Int column `n`. (The unguarded
   `present` write, the copy of `copy_effects`, and a creation's choice carry no conditions;
   `chosen_columns` attaches them only to values named by `of_name`, which an Int domain has
   none of.)
5. (P40) at `m' = 255`, a literal `k` on a nullable Int column is built as `Value(k+1)`
   narrowed to `u8`, so 255 becomes `Value(0)`, null.

A rule's premises and text can also differ: `build/preds/entity_rules.rs::push_unique` drops its
premise at one slot, and `build/preds/cross_rules.rs::count_premise` puts the slot count in its
text. The prover reads only a rule's binders and body, so these do not matter here.

*Proof sketch.* `int_max` is read in `core/build` at four places: the `Tick` guard
(`build/vars.rs::tick`), the literal range checks (`build/preds/atoms.rs::eq_atom`, `::int_term`,
`build/sets.rs::out_of_bounds`, all raising `StateDiag::IntLiteralOutOfBounds`, which is
`Severity::Error`), `Domain::of_number`, and `Domain::size` (in `lists_whole_domain`, which
refuses Int domains, and in the `Choose` lists of `build/sets.rs` and `build/transitions.rs`).
A `Choose` list is read a second time: `arm_guards` turns each listed value of a `Choose` with
conditions into a guard disjunct (item 4). Slot counts are read in `build/vars.rs` (the slots themselves and the
`IdentityStartSlots` error), in `build/preds/entity_rules.rs` and `build/preds/cross_rules.rs`
for vacuity premises and the `CountAboveBound` diagnostic, neither of which enters a rule's body
or an action. The variables `T` holds (D2) are chosen by what is read or written, not by `β`.
So, with no error at `β'`, the system is the same up to items 1 to 5. ∎

**Which items `Enc` covers.** (1) `Enc` states Int-typed domains as `≥ 0` and key domains as
sorts of any size. (2) A full list at `m` is encoded as `c ≥ 1` or `c ≥ 0`, which contains the
full list at `m'`, and a list that is not full holds literals that are the same at `m` and
`m'`. (3) `Enc` drops the `Tick` guard. A literal the model writes is the same `Value` at `m`
and `m'` because `of_number(k) = Value(k)` (or `k+1`) for `k ≤ min(m, m')`, as long as no
`u8` wraps (item 5).

Items 4 and 5 are not covered:

- **Item 4 (P43; fixed in #481: the builder keeps a choice of every number, `present` or a
  copy, in a bound-free form, `Effect::Choose::numbers`, which the encoder reads instead of the
  list, and the arm guard states it as one arm, `next.n != null`, which names no value of
  `β`; only the explorer, TLC and the generated code read the expanded list. What follows
  describes the code before #481).** `Enc::step` asserts every guard except the clock's, and `Enc::compare`
  reads each `Lit(v)` of the guard on a nullable Int as the number `v-1`. So the encoded step
  writes `present` only as one of `0 … m`. For `m' ≤ m` the guard at `β'` lists a subset of the
  values and implies the encoded guard, so F3 holds. For `m' > m` a step of `T_{β'}` that writes
  a value in `m+1 … m'` satisfies no encoded step, so F3 fails, and Theorem 1 can fail with it:
  the model in [Reproductions](#reproductions) prints `proved` at `m = 5`, with a kept mined

  Without the `.when` there is no such guard, the write is widened to `c ≥ 1`, and the same
  rule is `unproved: not inductive` at `m = 5`. `(Domain::Int, Present)` is
  `EffectRhs::None` (no write), so only nullable Int columns are affected. The fix is to widen
  the guard as the effect is widened; until it lands, Definition 3 leaves `m' > m` out for such
  models.
- **Item 5 (P40; fixed in #470, where such a column is the build error `DomainTooLarge`, so
  `m' = 255` is no bound the model builds at, and D1 makes it ill-formed;

  `Domain::of_variant` makes the 256th value of a nullable Enum null at every bound, so `ok` can

  [native.md](./native.md#the-state-store-and-its-encoding); #470 takes it up together with P40). That case does not depend on `β`, so it does not break Lemma U, but

**What stays intact.** The case `β' = β` needs no lemma. Changing only the instance counts

## Faithfulness of the encoding

**Definition 1 (the structure of a state).** For a state `s` of `T_{β'}`, `𝔄(s)` interprets
`E<i>` as the slots `[n'_E]` plus one extra element `⋆_E`; `nil<i>` as `⋆_E`; `zero<i>` as
slot 0; `v<k>(i)` as the index `s(v)[i]` for a slot `i`, and as the base value of `v` on `⋆_E`;
a key's value as the parent slot it names, or `⋆_P` for null; `now` as `s(now)`. For a step
`s →_{a,b} s'`, `𝔄(s, b, s')` extends `𝔄(s)` with `p_j ↦ b_j`, the post-state functions read
from `s'`, and each fresh constant set to the value the step chose (any domain value when its
condition is false).

**Proposition 2 (B1, over-approximation).** Assume claim I1 at `β`, so that `Enc` encodes
`T_β(M, σ)`. Then for every `β' ∈ Sc(M, β)` (Definition 3, which adds to the hypotheses of
Lemma U the conditions that exclude its items 4 and 5):

- (F1) `𝔄(s) ⊨ Decl` for every state `s` of `T_{β'}`;
- (F2) `𝔄(s) ⊨ Init` for every `s ∈ I_{β'}`;
- (F3) if `s →_{a,b} s'` in `T_{β'}`, then `𝔄(s, b, s') ⊨ Step_a`;
- (F4) for every predicate `φ` that encodes and every binding, `𝔄` satisfies `φ`'s encoding iff
  `expr.rs::eval` returns true on `s` (in frame `Pre`) or on `s'` (in frame `Post`).

*Proof sketch.* (F1) Each fact of `Decl` holds of `𝔄(s)`: indices lie in their (β-independent)
finite domains, Int-typed values are `≥ 0`, a non-optional key names a slot, `⋆` is absent. (F2)
D4 clause by clause: created entities at base; pre-existing slots present; `Start::Any` any
value; `Start::Identity` maps slot `i` to parent slot `i`, which is injective and not `⋆`.
(F3) Under I1 at `β` and Lemma U₀, the action of `T_{β'}` has the guards and effects `Enc`
encoded, up to items 1 to 5 of Lemma U (items 1 to 4 restate Lemma U₀; item 5 is a departure
of the build that #470 removed). Items 1 to 3 are covered; item 4 is covered when `m' ≤ m`, and item 5 does not arise
when `m' ≤ 254` or `m' = m`, which is what the conditions of Definition 3 add. Without them F3
can fail, and for P43 it does ([Reproductions](#reproductions)). The parameter constraints of `Enc` are implied by those of `T` (a
lowest absent slot is absent). The post-state functions equal `s'` because `Enc::step` and
`each_successor` apply the same updates in the same order ([Steps](#steps-step_a)); a havocked
write is satisfied by the value `T` wrote. Guards hold by (F4). (F4) By induction on `φ`, using
the agreement table of [Predicates](#predicates) for `Cmp`, and the facts that `Forall`,
`Exists`, and `Count` range over present rows on both sides and `⋆` is never present. ∎

What this rests on, beyond the sketch:

- **Reading, not mechanical checking.** No Kani harness or shadow twin covers `core/prove/`.
  `Enc::compare` and `expr.rs::compare` are two implementations tied by inspection and by the
  differential tests below (P3).
- **Differential tests.** `cli/tests/proof_equivalence.rs::no_proved_rule_has_a_bounded_counterexample`
  proves every sample and checks that BFS finds no violation of a proved rule at 1, 2, and 3
  instances per entity and at `int_max + 2`; `::no_proved_rule_has_a_bounded_counterexample_in_the_corpus`
  does the same on every engine-corpus case. These test (F1) to (F4) only through their
  consequence, and only at those bounds. The corpus cases `z3_int_and_now_boundary` and
  `z3_now_past_the_top` pin the clock widening from both sides. Two limits weaken this evidence
  (P44): a cone whose BFS does not finish under the test's `STATE_CAP = 300,000` is skipped
  (module doc of `proof_equivalence.rs`; since #490 the test prints each comparison it skips),
  and without z3 on `PATH` the whole test is skipped
  with a printed reason unless `RDRA_REQUIRE_Z3=1` is set (`found_or_skip`; CI sets it, so this
  skip affects local runs only). The wider-Int axis
  did not catch P43, because no sample or corpus case has a `.when`-guarded `present` write to a
  nullable Int.
- **The preamble.** (F1), (F2), and `I_{β} ≠ ∅` imply that `Decl ∧ Init` is satisfiable. If
  an encoder bug made it unsatisfiable, every initiation check would be `unsat` and every
  consecution check of a set holding initially could be too, so every rule would be `proved`.
  Since #482 every proof checks it first with a canary candidate `false`, which must fall at
  initiation (`premise`), and proves no rule when it survives (P3). On the transcripts of
  `examples/prove_transcript.rs` for `order.rdra`, `check_met.rdra`, `one_to_one_shared.rdra`
  (formal-verification samples) and `patent-ops`, `Decl ∧ Init` plus the activation
  implications is `sat` under z3 5.1.0 with MBQI on ([Reproductions](#reproductions)); that is a
  spot check, not a guarantee.

## Induction and Houdini

<!-- derived-from ../formal-verification.md#proofs-for-any-number-of-rows -->

### Relative induction

A state rule `R` is rarely inductive alone: a step can break it from a state where it holds but
which is not reachable. The standard remedy is to prove a set `K ∋ R` inductive together
(Definition in [Notation](#notation)); each member then holds in every reachable state, and the
other members act as lemmas. `prove` searches for such a set among the candidates with Houdini
(Flanagan and Leino, 2001): start with every candidate, drop each one some initiation or
consecution check breaks, and repeat until a pass over every check drops nothing. The search is
1-induction (Sheeran, Singh, and Stålmarck, 2000, with `k = 1`) over a set that only shrinks.

### The rounds

`core/prove/mod.rs::prove_round` runs one Houdini search:

1. **Candidates.** Every selected rule not in `refuted`, the built-in lemmas (`lemmas`), the
   mined lemmas with their wait stage (`mine::Mined::wait`: 0, 1 for the fine ones and the
   counts, 2 for ∀∃), and the CTI clauses of earlier rounds. A formula that does not encode is
   left out (a rule becomes `out of scope`).
2. **Activation literals** (#434). Each candidate `k` is declared once per solver as
   `act_k : Bool` with `act_k ⇒ ⟦ψ_k⟧^Pre`. A consecution check asserts `act_k` for the members
   of the current set. The literals of a wait stage are declared only when the stage joins
   (#445), so a proof that never needs a stage sends z3 nothing of it.
3. **Initiation**, once per candidate, before the stage it belongs to joins: `Init ∧
   Viol(ψ, Pre)`; `sat` is `Fall::Initial`, `unknown` is `Fall::GaveUp(None)`.
4. **Consecution**, by passes over the actions. For action `a`, the hit set is every member `k`
   with `reads(ψ_k) ∩ writes(a) ≠ ∅` (`breaks`). Under one scope (`Step_a` and the members'
   literals) each hit candidate is checked: `sat` is `Fall::Step(a)`, `unknown` is
   `Fall::GaveUp(Some(a))`. A candidate that falls stays asserted for the rest of that action's
   checks, so the answers do not depend on the order of the checks. Passes repeat until one
   removes nothing.
5. **Waiting stages.** When a rule fell after initiation, the next stage with a member that
   holds initially joins; the rules that fell after initiation return to the set; step 4 runs
   again. Lemmas that fell do not return.
6. **CTIs**, for each rule that fell: on solver 0, after `(reset)`, with MBQI on, the kept set
   asserted directly (`assume`), and the rule's pre-state formula.

`prove_offered` then runs up to `STRENGTHEN_ROUNDS = 2` more complete rounds when the CTI stage
produced new clauses ([CTI clauses](#cti-clauses)); the result is that of the last round.

### MBQI toggling

Steps 3 to 5 run with `smt.mbqi false` (#421). Without model-based quantifier
instantiation (Ge and de Moura, 2009), z3 still proves `unsat` by E-matching, but in practice
it answers `unknown` on almost every query it would find a model for, because `Decl` contains
quantifiers; the candidate then falls as `GaveUp`, exactly as with `sat`. MBQI is a completeness device: turning it off cannot turn a satisfiable query into
`unsat`, so it changes no `proved`. The measured effect on every sample on one solver was 150 s
to 68 s of proof with the same `Proof` (code comment in `prove_round`). The CTI stage needs a
model, so it turns MBQI back on.

### Step pruning

**Lemma F5 (B6).** If `reads(ψ) ∩ writes(a) = ∅`, then `Decl ∧ Step_a ⊨ ⟦ψ⟧^Pre ⇔ ⟦ψ⟧^Post`.

*Proof.* `Enc::step` gives a variable a new post-state function only through `set`, called for
`Create` (existence), `Assign`, single-target `Transition`, forks of `Transition` and
`Choose` (the variable written), and `Delete` (existence and the entity's columns); `now_n`
differs from `now` only under `Tick`. `core/cone.rs::effect_writes` lists, for the same
effects, existence; the variable; existence, columns, and keys; and `now`. So every variable
whose post-state function differs from its pre-state function is in `writes(a)`. `⟦ψ⟧^F` reads
the functions of `reads(ψ)` and of the existence of its binders and quantified entities (all in
`reads(ψ)` by `pred_reads`), `now` if `ψ` reads it, and row constants. All of these agree in
the two frames. ∎

So a member that `a` does not hit cannot be broken by `a`, and skipping its check loses nothing.

### The kept set is inductive

**Proposition 4 (B5).** Assume z3's `unsat` answers are correct and each is taken for the
check that asked it (H1, H4). The set `K` a round keeps (the
candidates with no fall and a joined stage, `Set::contains`) is inductive relative to `Enc`.

*Proof.* Every member passed initiation: wait-0 candidates before the first pass, later stages
when they joined, and the rules that returned had passed it before they fell. The loop of step 4
exits only after a full pass over every action in which no member fell, and step 5 either adds
nothing (the proof ends) or is followed by another such loop. In that last pass the set is `K`
throughout, each action's scope asserts exactly the literals of `K`, and every hit member got
`unsat`. A non-hit member is preserved by Lemma F5. A model of `Decl ∧ Step_a ∧
⋀_{χ∈K}⟦χ⟧^Pre ∧ Viol(ψ, Post)` expands to a model of the checked query by setting `act_χ` true
for `χ ∈ K` and false otherwise, so that query being `unsat` makes the consecution condition
hold. ∎

`unknown` never helps a candidate: it is a fall (B12). A `SolverError` aborts the whole proof.

### Maximality

The guide says the prover "keeps the largest set of rules and lemmas that is inductive
together". That holds only in a narrow sense.

**Proposition 5.** If every z3 answer were exact (no `unknown`), the first stage computes the
largest inductive subset of the wait-0 candidates (classical Houdini: a candidate is removed only
when it is in no inductive subset of the current set). The final `K` need not be the largest
inductive subset of all candidates offered, for four reasons:

1. `unknown` counts as a fall, and with MBQI off in practice almost every satisfiable check
   returns `unknown`, because `Decl` contains quantifiers, so a candidate can fall on a query
   z3 gave up on although it was unsatisfiable. How often that
   happens is not known: the `unknown` counts in formal-verification.md, "Budgets", do not
   separate satisfiable queries from undecided ones, so they are no evidence either way.
2. A lemma that fell before a stage joined never returns, though the joined lemmas might have
   made it inductive; only rules return (step 5).
3. A stage joins only when a rule fell after initiation; a stage that would let more lemmas
   survive does not join when every rule is already proved.
4. The CTI rounds restart Houdini with more candidates, and the result is the last round's.

None of these touches soundness, which rests on Proposition 4 alone. They affect which rules are
proved and which `lemma:` lines print. P5 records the overstatement.

## The soundness theorem

**Definition 3 (scope of a proof).** For a run at `β = (n, m)` under scope `σ`, `Sc(M, β)` is
the set of bounds `β' = (n', m')` such that `TransitionSystem::build(M, β', σ)` reports no
error, every Int literal of the model is at most `m'`, and:

- `m' ≤ m` when `T` has an `ArmCondition` guard built from a `Choose` that lists every value
  of an Int-typed domain, which at the pinned commit means a `.when`-guarded
  `sets(UC, E.n == present)` on a nullable Int column (P43, Lemma U item 4);
- `m' ≤ 254` when the model has a nullable Int column (P40, Lemma U item 5), unless `m' = m`.

By D1, `1 ≤ n'_E ≤ 255` and `1 ≤ m' ≤ 255` (`cli/src/export.rs::checked_bounds` rejects 0).
`β ∈ Sc(M, β)` whenever the run builds without error: for `β' = β` Lemma U holds trivially, and
for `m' = m` items 4 and 5 are the same in `T` and `T_{β'}`.
Before #470, at `m = 255` with a nullable Int, the build departed from D8 (P40, a failure of
claim I1 at `β`). The theorem, whose encoding reads the build, then said nothing about
`T_β(M)` itself. Since #470 that bound is ill-formed (D1). These conditions describe the code at the pinned commit.
The fix for P43 (widening the guard as the effect is widened), in #481, removes the first one.

**Theorem 1 (B2).** Assume (H1) z3 answers `unsat` only for unsatisfiable queries, (H2) the
text `smt.rs` prints means the `Expr` it was built from, (H3) Proposition 2 holds for every
`β' ∈ Sc(M, β)`, and (H4) the prover takes each z3 answer for the check that asked it
([the answer reader](#the-answer-reader): `Z3::exec` reads a batch's output up to its
echoed marker, and `Solver::check_sat` reads the first line of it as the answer), and (H5)
claim I1 holds at `β`: the build returns `T_β(M, σ)`, so `Enc` encodes it (Proposition 2
assumes H5). If `verify --prove` prints `proved: R` (`Verdict::Proved`), then for every
`β' ∈ Sc(M, β)`, `T_{β'}(M, σ) ⊨ R` in the sense of D16.

The theorem is conditional on H3, and H3 is a proof sketch, not a checked fact. Without the
condition `m' ≤ m` for the P43 construct in `Sc(M, β)`, H3 is false and the theorem's
conclusion fails on the model in [Reproductions](#reproductions).

*Proof.* `Verdict::Proved` is given to a rule exactly when it has no fall in the round whose
`Proof` is returned, that is, when it belongs to the kept set `K` of that round, or to a
certificate the reuse round accepted ([The certificate cache](#the-certificate-cache)); in both
cases `K` is inductive relative to `Enc` by Proposition 4 or Proposition 7. Fix `β' ∈ Sc(M, β)`.
By induction on the length of a finite trace `s_0 → … → s_j` of `T_{β'}` we show
`𝔄(s_j) ⊨ ⋀_{χ∈K} ⟦χ⟧^Pre`:

- *Base.* `s_0 ∈ I_{β'}`, so `𝔄(s_0) ⊨ Decl ∧ Init` by F1 and F2. For `χ ∈ K`,
  `Decl ∧ Init ∧ Viol(χ, Pre)` is unsatisfiable (initiation, with H1, H2, and H4), so
  `𝔄(s_0) ⊨ ⟦χ⟧^Pre`.
- *Step.* `s_j →_{a,b} s_{j+1}`. By F1 and F3, `𝔄(s_j, b, s_{j+1}) ⊨ Decl ∧ Step_a`, and by the
  hypothesis it satisfies `⋀_K ⟦χ⟧^Pre`. By consecution (with H1, H2, and H4) and Lemma F5 it satisfies
  `⟦χ⟧^Post` for every `χ ∈ K`. The post-state functions of that structure are those of
  `𝔄(s_{j+1})`, so `𝔄(s_{j+1}) ⊨ ⋀_K ⟦χ⟧^Pre`.

`R ∈ K` with `all_rows = false`, so `⟦R⟧^Pre` says that every tuple of present rows satisfies
the body; by F4 that is D16 on `s_j`. ∎

**Remarks on the hypotheses.**

- **Scope `σ`.** The theorem is about `T(M, σ)` (D24). Under `--buc`, `--without-usecase`,
  `--without-buc`, or `--actor`, the encoded system lacks the left-out actions, and `proved`
  says nothing about the whole model. The `scope:` header line names `σ`, and the `OK:` line
  says `in the selected scope`. Before #483 the `proof (...)` header, every `proved:` line, and
  the closing clause did not ([Reproductions](#reproductions), P4); since #483 each of them,
  the `lemma:` lines and the counts say `in the selected scope` too.
- **What "any Int value" means.** Inside `Enc`, Int-typed variables range over all non-negative
  integers. As a statement about the model's systems, the theorem covers each `m'` from the
  largest literal to 254 or 255; no `T_{β'}` with a larger top exists (D1). Negative values are
  outside both. A model with the P43 construct is the exception: there the theorem covers
  only `m' ≤ m`, and the printed "any Int value" is false at the pinned commit. `ProofTally::clause`
  prints it for every model, so it overstates for such a model and omits "non-negative" for
  every model; `Verdict::Proved`'s doc comment ("at the stated value bounds") understates it
  for the others (P2, P43).
- **Instance counts.** `Enc` has no count, so the theorem holds for every `n'` at which the
  build has no error, at `m' = m`, including for models with the P43 construct. Counts above
  255 are not systems `T` defines.
- **Satisfiability of premises.** If `Decl ∧ Init` were unsatisfiable, the conclusion would
  still follow from the hypotheses, because H3 includes F1 and F2; the risk is that H3 is false,
  and that would show only through the differential tests (P3).

**Corollary 6 (a cone decided by proof, B16 second part).** `BfsCone::decided_by_proof`
(`cli/src/verify/bfs.rs`) turns a safety cone that stopped at the memory limit with no violation
into `ok` when the cone has no `after` assertion and every invariant of the cone (by name) is in
`ProofRun::proved`. `β ∈ Sc(M, β)` whenever the run builds without error (Definition 3), so by
Theorem 1, under its hypothesis H5 (claim I1 at `β`), each of those invariants holds on
`T_β(M, σ)`. P43 does not affect this, since it
concerns only bounds above `m`. Before #470, at `m = 255` with a nullable Int, the built
system was not `T_β` (P40, a failure of claim I1). A cone
stopped at `--max-states` is not changed, which is a choice, not a limit of the theorem.

## Candidates and the trust base

Proposition 4 holds for any candidate set, so no candidate source can make `proved` unsound.
A candidate's source matters only for which rules get proved. The *trust base* of `proved` is
H1 to H4; it contains no candidate, no mining result, no CTI, and no user lemma.

### Built-in lemmas

`core/prove/mod.rs::lemmas` offers, per entity, "an absent row holds base values" (needed
because `Enc` does not pin absent rows, while `T` creates rows at base), "no row of an entity no
action deletes is deleted", and, per key, "a present row's key never names an absent parent
row". All are wait 0.

### Mined lemmas (B9)

`core/prove/mine.rs::mine` explores, with BFS, each entity cone and each selected rule's cone of
`T`, and of the one-instance twin `mining_twin` when it builds as `T` does, each up to
`STATE_CAP = 50,000` states, and turns what every reached state shows into candidates:

| Shape | Wait | Source |
|---|---|---|
| a present row is one of the reached patterns of its cone's row variables (at most 64), and each column's values and value pairs | 0 | |
| a child row with its parent: whole, per parent column | 0 | |
| one child column with one parent column, or with two when its pairs do not imply it | 1 | #440 |
| count lemmas: a parent row with a value a count guard's step writes has at most / at least the guard's `k` children by that key (all, or those the guard pins), `k ≤ 7` for at most (`COUNT_MAX = 7`) and `k ≤ 8` for at least | 1 | #446 |
| ∀∃: while a present row of `E` holds `a`, some present row of `F` holds `b`, no key between them; from the run's bounds only | 2 | #448 |

A mined lemma is a guess from a finite instance, in the manner of invisible invariants (Pnueli,
Ruah, and Zuck, 2001) and of the data-driven inference of DistAI and DuoAI: it may be false at
other bounds, or depend on a capped run. Houdini keeps it only if it is inductive with the rest,
so a capped or wrong mining costs proofs, not soundness. The order of exploration is fixed
(`in_parallel` gathers results in cone order), so the candidates do not depend on threads.

### CTI clauses

When a rule falls, `core/prove/strengthen.rs` reads the CTI model's pre-state over the step's
parameters and the rule's binders (`diagram`): the present rows, each once; the literals that pin
their columns and marks; their keys to one another or to null; and that two rows of one entity
differ. If there are at most `LITERAL_CAP = 40` literals, the clause `¬(l_1 ∧ … ∧ l_r)` over
those rows is checked for initiation and for consecution relative to the kept set plus the rule
(`inductive`, MBQI on, the lemma rlimit). If it passes, literals are dropped one at a time in a
fixed order while it still passes, and unused binders are trimmed (`generalize`, `trim`). This is
IC3's inductive generalization of a counterexample to induction (Bradley, 2011; Eén,
Mishchenko, and Brayton, 2011), without IC3's frames or its recursion into predecessors. A
surviving clause is a plain candidate of the next round (#450). Its relative induction used the
rule as a hypothesis, so it proves nothing by itself; Houdini decides it with the rest.

### User lemmas (`.lemma()`)

A rule marked `.lemma()` (`core/prove/mod.rs::lemma_invariants`) is a selected rule like any
other: `Origin::Rule`, wait 0, the rule rlimit (20,000,000), and it prints `proved: lemma …` or
`unproved: lemma …` and is left out of the rule counts (`cli/src/prove.rs::run_proof`). Because
it is a rule:

- it adds nothing to the trust base: it is kept only if inductive with the rest (B11);
- when it falls after initiation, it opens the waiting stages like any rule;
- a certificate is reused only if it keeps every rule, user lemmas included (`reusable`,
  `holds_every_rule`).

A lemma, unlike other rules, may read marks: `E.in_run(UC)` reads the run mark of D10 and
`E.raised(Ev)` the latch of D11 (#438; language-reference.md, "Marks in a lemma"). The encoding
reads them as row functions like any column. Reading a mark adds nothing to the trust base
either.

`verify` seeds no BFS cone from a lemma (`cli/src/verify/mod.rs` filters lemma targets) and never
escalates one (`run_proof` removes lemmas from `ProofRun::unproved`). But a lemma whose reads lie
inside another selected rule's cone is checked by that cone. Then a false lemma is `refuted` and
fails the run with a counterexample, contrary to B11's "never `refuted`" and formal-verification.md's
"`verify` runs no cone for it" ([Reproductions](#reproductions), P41). When BFS does not reach
the violation, Houdini drops the false lemma (`unproved: lemma …: not inductive`), and the rule
it was meant to help is decided without it. Since #490 the docs say a covering cone checks a
lemma (P41), and `prove_cli::a_false_lemma_is_refuted_where_bfs_reaches_it_and_dropped_where_not`
covers both paths (P5).

## Verdicts other than proved

<!-- constrained-by ./semantics.md#verdicts -->

- **`unproved: R: not inductive` (B17).** The CTI stage asserts `Step_a`, every kept candidate,
  `⟦R⟧^Pre`, and `Viol(R, Post)`, and prints the model (`read_cti`). The pre-state satisfies `R`
  and every kept candidate, rules and lemmas alike; the printed phrase "every proved rule"
  understates this (P5). The pre-state is a model of `Enc`, not necessarily the image of a
  reachable state of any `T_{β'}`: a CTI is a counterexample to induction, not a counterexample.
  It may also have rows or Int values beyond `β`.
- **`unproved: R: z3 gave up on A` (B12).** `Fall::GaveUp` or `Fall::Unknown`, and no CTI step
  was found with MBQI on. Nothing is claimed.
- **`unproved: R: an initial state violates it`.** `Init ∧ Viol(R, Pre)` is satisfiable. The
  model may have more rows or other start values than `I_β`, so this is a violation of some
  `T_{β'}` only if the model corresponds to an initial state of one; `Unproved::Initial`'s doc
  said the bounded engines report it, which holds only when the violation fits `β` (P4; the
  doc says so since #483).
- **`out of scope: R: why`.** `R` does not encode. No claim.

A counterexample (D23) comes from BFS or TLC, never from z3. The two are joined per rule: BFS's
violation makes the rule `refuted`, and escalation looks for one past `β`
([Interaction with BFS](#interaction-with-bfs)).

## Budgets, solver count, and determinism

**Values.** `ProveOptions::default` sets `rlimit = 20,000,000` for a rule (user lemmas included)
and `lemma_rlimit = 2,000,000` for built-in, mined, and CTI lemmas; `strengthen::generalize`
checks a clause at the lemma limit. formal-verification.md's "2,000,000 for a lemma" is right
for the prover's lemmas and wrong for `.lemma()` rules (P5).

**Measured headroom** (formal-verification.md, "Budgets", on z3 5.1.0): on every sample on 2
solvers, and on the formal-verification samples, insurance-claim-ops, and oidc-auth on 1 and 3,
a check that keeps its candidate spends at most 161,000 units for a rule (1/124 of its limit) and
116,000 for a lemma (1/17); on 4 solvers a lemma check spent 144,000 (1/14). No such check runs
out. `cli/tests/proof_equivalence.rs` meters every check and fails when a keeping check spends
more than a tenth of its limit, when a check runs out (`canceled`), or when an answering check
spends nine tenths (`only_a_check_that_ran_out_fails_the_headroom_check`,
`the_headroom_check_fails_when_a_check_runs_out`).

**Determinism (B13, B14).** An rlimit counts z3's internal work, not time, so the answer of a
check does not depend on load. It does depend on:

1. the z3 version: `VERIFIED_Z3 = ["5.1.0"]` (pinned by `flake.nix` and `flake.lock`), and
   `unverified_z3_note` prints a note under any other version, or an unreadable one;
2. the query text, fixed by the encoding;
3. the solver's history. Each solver is its own process, and `violated_each` deals checks to
   solver `h` by index (`skip(hand).step_by(hands)`), so each solver receives a sequence of
   commands that depends only on the encoding and on the number of solvers, not on thread timing.

So for one z3 version and one solver count, a proof is a deterministic function of the encoding,
assuming z3 is deterministic on equal input (its default seed is fixed). The solver count is
`RDRA_JOBS`, else `min(cores, 8)` (`crates/rdra-ish-core/src/parallel.rs::jobs`), so it differs
between machines. Independence from it is empirical:
`a_proof_is_the_same_on_any_number_of_solvers` compares 1 against 3 solvers on a subset of the
samples, and proof digests were compared on 40 roots by hand: on 1 and 4 solvers in #434, and
on 1, 2, and 3 solvers in #445.
formal-verification.md records a lemma check in food-permit-ops that z3 gives up on by itself on
1 to 6 solvers and that runs out of its limit on 3; both are `unknown`, so the verdict is the
same, but the case shows that history changes what a check spends (P5).

## The certificate cache

`cli/src/prove.rs` keeps, per model and rule selection, a file under the user's cache directory
holding the z3 version line, the digest of the round (`core/prove/mod.rs::digest`: a tag, the
rdra-ish version, the options, `Decl`, `Init`, every `Step_a`, and each candidate's origin,
rlimit, wait, and formulas), and the indices of the set the last proof kept. The file carries its
own checksum; a damaged one is ignored. `RDRA_ISH_NO_PROOF_CACHE` turns it off.

**Proposition 7 (B15).** A reused certificate makes a rule `proved` only if the set it names is
inductive relative to the current `Enc`.

*Proof.* `reusable` accepts the offered set `K` only if every index is a current candidate,
every rule candidate is in `K`, every candidate of `K` passes initiation, and, for each action,
every member it hits gets `unsat` under `Step_a` and the literals of exactly `K`. That is the
last pass of Proposition 4 for `K`. ∎

The proof does not use the digest. The digest is what makes reuse *output-preserving*: equal
digests mean the earlier run sent the same rounds, so with a deterministic z3 it kept the same
set, and the output is byte-identical
(`a_certificate_is_reused_only_when_it_rechecks_and_changes_no_proof`,
`a_cached_certificate_changes_nothing_a_run_prints`). The digest tag (now 3) must be bumped by
hand when the order of checks changes (#445, #448). A certificate never carries CTI clauses, so
a proof that needed one misses the cache every time (#450). A failed reuse costs the round, and
the solvers are reset before Houdini runs as usual
(`a_certificate_whose_round_fails_changes_no_proof`).

## Interaction with BFS

<!-- constrained-by ./semantics.md#verdicts -->

**Refutation (#423).** `cli/src/verify/refuted.rs::refuted` collects every invariant a safety
cone of the same run violated, matched by name and site, and passes them to `prove` as
`refuted`; they are not candidates and print `refuted: R (BFS counterexample at k instances)`.

**Proposition 8 (B16, first part).** Removing candidates never makes a `proved` unsound
(Proposition 4 holds for any candidate set). If (a) the BFS violation is a reachable state of
`T_β(M, σ)` and (b) every z3 answer is exact, removing `R` changes no other rule's verdict.

*Proof sketch.* By (a) and Theorem 1, `R` is in no inductive set, so exact Houdini drops it in
any run that holds it. Its fall can open a waiting stage; when every other rule was already
kept, the stage only adds candidates, and exact Houdini over a larger start set keeps a superset
of the earlier kept set, so those rules stay proved. When another rule fell, the stage opens
either way. ∎

Neither hypothesis is guaranteed. Under P1, a cone that leaves a raised mark out can report a
state the event order forbids, so (a) can fail: a true rule is then never tried, prints
`refuted`, and any other rule that needed it as a lemma may lose its proof. Without (b), the
order and content of checks differ with and without `R`, and an `unknown` can land differently.
The test `a_refuted_rule_left_out_changes_no_other_verdict` checks the conclusion on the
formal-verification samples and every engine-corpus case (P42). No `proved` is wrong in either
case.

**Escalation (#433).** For a rule `unproved` by z3 whose own safety cone ran to completion
without violating it (`cli/src/verify/escalate.rs::passed_at`), the cone is explored again at
`n+1` and `n+2` instances per entity (`grown`), each run held to ten times the store of the
first (`GROWTH`) and to what the memory pool has left. The rebuilt system must pass
`same_system`. A violation found there is printed as an error with its trace and fails the run.
Its status is that of any BFS counterexample (D23): a behavior of `T_{β'}` except under P1, and
`k` may understate the instances needed (P11). Escalation adds bounded evidence to an unproved
rule; it never changes a `proved`.

**Scheduling (#424).** The proof starts after the safety cones and runs beside the property and
whole-model passes, so it uses the refuted set of the safety pass only.

**CTI against counterexample.** The CTI of an unproved rule and a BFS counterexample of the same
rule are different objects: the first is a state of `Enc` and need not be reachable, the second
is a trace of `T` (modulo P1). The tools do not match one against the other (an owner decision
in #421).

## Reproductions

Each run used the release build of `fb6928c7` and z3 5.1.0, at one or two instances, each under
a second. The models are short enough to quote in full. None of them is yet a test or corpus
case: each is marked *repro pending in repo* with the fix lane that adds it, and the marker
gives way to the test's path when that lands.

**P4, a proof under a scope** (in the repository since #483:
`prove_cli::a_proof_under_a_scope_says_so_on_every_proved_line`)**.**

```rdra
entity Order "o" {
  id: Int @pk
  status: Enum(open, closed) @default(open)
}
usecase Place "p"
usecase Close "c"
creates(Place, Order)
updates(Close, Order)
transitions(Close, Order.status, open -> closed)
forbidden(Order, status == closed)
```

`verify --prove --without-usecase Close` prints `scope: --without-usecase Close (1 use case
assumed not to run: Close)`, then `proof (Z3 version 5.1.0 - 64 bit): 1 state rules, for any
number of rows and any Int value`, `proved: Forbidden_Order_0`, and `OK: no errors in the
selected scope, within 2 instances per entity, Int 0..5; 1 of 1 rules proved for any number of
rows and any Int value`. Without the scope the same rule is `refuted: Forbidden_Order_0 (BFS
counterexample at 2 instances)`. The proof is right about `T(M, σ)`; only the `scope:` line and
the start of the `OK:` line say that `σ` is not the model.

**P40, the top Int value of a nullable column** (in the repository since #470: the engine-corpus case `width_nullable_int_top.rdra` and `check_cli::a_nullable_int_column_takes_no_range_past_254`)**.**

```rdra
entity Item "i" {
  id: Int @pk
  n: Int @null
}
usecase Add "a"
usecase Top "t"
creates(Add, Item)
updates(Top, Item)
sets(Top, Item.n == 255)
forbidden(Item, n == 255)
```

`verify --prove --int-range-max 255 --instance-count 1` prints `proved: Forbidden_Item_0`, the
mined lemma `a present Item row's n is one of {null}`, `result: ok`, and `1 of 1 rules proved for
any number of rows and any Int value`. The same model with 254 in place of 255, at
`--int-range-max 254`, prints `refuted: Forbidden_Item_0 (BFS counterexample at 1 instance)`.
At 255 the write's literal is built by `Domain::of_number` as `Value(255 + 1)` narrowed to
`u8`, that is `Value(0)`, null, so both BFS and z3 check a system in which the use case writes
null. The rule's literal is not narrowed: `atoms.rs::eq_atom` builds `n == 255` as
`Term::Int(255)`, compared as a number, and a null `n` does not equal it, so the rule holds in
the built system, which departed from D8 (I1 failed). (In a debug build, `n as u8 + 1` overflows and panics instead.)

A `present` write produces null at 255 as well, once the column's domain is nullable Int. When
the rules read only whether `n` is null, the column gets the `Nullable` domain (null or
present) and never takes the nullable Int path. Adding a numeric rule forces it:

```rdra
entity Item "i" {
  id: Int @pk
  n: Int @null @default(0)
}
usecase Add "a"
usecase Fill "f"
creates(Add, Item)
updates(Fill, Item)
sets(Fill, Item.n == present)
forbidden(Item, n == null)
forbidden(Item, n < 0)
```

At `--int-range-max 5 --instance-count 1` both rules are `proved` and the run is `ok`. At 255,
BFS refutes `Forbidden_Item_0` with the step `Item#1.n: 0 -> null`: the `Choose` list
`Value(i as u8)` for `1 ≤ i < 257` wraps at its last entry, `i = 256`, to `Value(0)`, null. This lies inside the
`m' ≤ 254` exclusion of Definition 3, so it is no new gap in the theorem, but it shows that the
`present` path is affected too.

**P43, a `.when`-guarded `present` write past the run's top** (in the repository since #481:
the engine-corpus case `z3_guarded_present_past_the_top.rdra` and
`prove_cli::a_guarded_present_write_reaches_past_the_int_range`)**.**

```rdra
entity Item "i" {
  id: Int @pk
  open: Bool @default(true)
  n: Int @null
}
usecase Add "a"
usecase Fill "f"
creates(Add, Item)
updates(Fill, Item)
condition IsOpen "o"
holds(IsOpen, Item.open == true)
sets(Fill, Item.n == present).when(IsOpen)
forbidden(Item, n > 5)
```

`verify --prove --int-range-max 5 --instance-count 1` prints `proved: Forbidden_Item_0`, the
kept lemma `a present Item row's (open, n) is one of {(true, null), (true, 0), …, (true, 5)}`,
`result: ok`, and `1 of 1 rules proved for any number of rows and any Int value`. At
`--int-range-max 7` the same model prints `refuted: Forbidden_Item_0 (BFS counterexample at 1
instance)` with the step `Item#1.n: null -> 6`. `(1, 7)` meets every condition of Definition 3
except `m' ≤ m`: the build reports no error, the literal 5 is at most 7, and `7 ≤ 254`. The lemma
can be kept because the encoded step of `Fill` asserts the guard built at `m = 5`, which allows
only `n ∈ {0, …, 5}`. Without `.when(IsOpen)` the same rule prints `unproved: Forbidden_Item_0:
not inductive; Fill(Item#1) breaks it …` at `m = 5`, as it should.

## Threats to validity

- **Faithfulness is argued, not checked.** Proposition 2 is a reading of `encode.rs` against
  `explore/moves.rs` and `expr.rs`. The differential tests check its consequence at 1 to 3
  instances and `int_max + 2` on the samples and the corpus, skip cones past 300,000 states,
  and skip everything without z3 unless `RDRA_REQUIRE_Z3` is set (P44). A mismatch that only
  matters at larger bounds, in a large cone, or on a construct no sample uses goes unseen. P43
  is such a construct.
- **Uniformity is argued, not checked.** Lemma U rests on reading every use of `int_max` and
  of slot counts in `core/build`, and such a reading can miss a read: the one that gives item 4
  (P43), `arm_guards` reading a `Choose` list a second time, was found by a review, not by a
  test ([Errata](#errata)). CI checks the list of sites the reading covers against the code
  ([the sites](#uniformity-in-the-bound) under Lemma U), so a new direct read of `int_max` or
  call of `Domain::of_number` or `Domain::size` in `core/build` fails a check; a read of the
  item-4 kind does not. P40 breaks uniformity at `m' = 255`, and P43 breaks it at every `m' > m`
  for one construct. Other breaks of this kind may exist. A future builder change that reads
  `β` into a rule or a guard, as `lists_whole_domain` did before #429, would break Theorem 1 at
  other bounds without any test failing, unless `proof_equivalence`'s wider-Int axis happens to
  cover it. A run-time check that compares the system at `β` with the one at a larger `m` would
  catch this class, and `same_system` does not do that.
- **z3.** H1 is an assumption. The queries are outside a decidable fragment (Int-valued
  functions over uninterpreted sorts, quantifier alternation in ∀∃ lemmas and guards, #427), so
  `unknown` is expected; it costs proofs only. A z3 bug that answers `unsat` wrongly would yield
  a wrong `proved`; `proof_equivalence` would see it only if BFS reaches the violation.
- **Determinism across machines** depends on the solver count matching on every machine or on
  B14 holding, which is empirical.
- **Scope.** A proof under a partial-run flag is a proof of a smaller system (P4); since #483
  every `proved:` line says so.
- **The printer and the parser.** H2 rests on `smt.rs`'s typed builder and its unit tests. H4
  rests on z3 keeping the output protocol of [the answer reader](#the-answer-reader);
  the reader fails closed on any line that is not an answer, but no test drives it, and an
  answer that belongs to another check would go unseen. The
  model reader (`Sexp`, `read_cti`, `strengthen::diagram`) affects only CTIs and candidate
  clauses, never `proved`.

## Related work

- **Houdini.** C. Flanagan and K. R. M. Leino, "Houdini, an Annotation Assistant for ESC/Java",
  FME 2001. The prover's candidate loop is Houdini over a fixed template set, with staged
  candidates added on failure; S. K. Lahiri and S. Qadeer, "Complexity and Algorithms for
  Monomial and Clausal Predicate Abstraction", CADE 2009, study the greatest-fixpoint property
  that Proposition 5 shows the staging gives up.
- **k-induction.** M. Sheeran, S. Singh, and G. Stålmarck, "Checking Safety Properties Using
  Induction and a SAT-Solver", FMCAD 2000. The prover uses `k = 1` with strengthening lemmas
  instead of a larger `k`.
- **IC3/PDR.** A. R. Bradley, "SAT-Based Model Checking without Unrolling", VMCAI 2011; N. Eén,
  A. Mishchenko, and R. Brayton, "Efficient Implementation of Property Directed Reachability",
  FMCAD 2011. `strengthen.rs` borrows the CTI diagram and the literal-dropping generalization,
  without frames or predecessor recursion.
- **Invariants of parameterized systems.** A. Pnueli, S. Ruah, and L. Zuck, "Automatic
  Deductive Verification with Invisible Invariants", TACAS 2001, generalize invariants from a
  small instance and check them for all sizes, as mining from BFS at the run's bounds and at one
  instance does. O. Padon, K. L. McMillan, A. Panda, M. Sagiv, and S. Shoham, "Ivy: Safety
  Verification by Interactive Generalization", PLDI 2016, keep queries in EPR so they are
  decidable; this encoding does not (Int columns, ∀∃). A. Karbyshev, N. Bjørner, S. Itzhaky,
  N. Rinetzky, and S. Shoham, "Property-Directed Inference of Universal Invariants or Proving
  Their Absence", CAV 2015 (UPDR), and A. Goel and K. Sakallah, "On Symmetry and Quantification:
  A New Approach to Verify Distributed Protocols", NFM 2021 (IC3PO), lift IC3 to quantified
  invariants over unbounded sorts. J. Yao, R. Tao, R. Gu, J. Nieh, S. Jana, and G. Ryan,
  "DistAI: Data-Driven Automated Invariant Learning for Distributed Protocols", OSDI 2021,
  enumerates ∀ candidates pruned by reachable states and keeps the inductive ones. J. Yao,
  R. Tao, R. Gu, and J. Nieh, "DuoAI: Fast, Automated Inference of Inductive Invariants for
  Verifying Distributed Protocols", OSDI 2022, extends this to ∀∃ candidates; #448's ∀∃ lemmas
  follow that pattern (#428).
- **The solver.** L. de Moura and N. Bjørner, "Z3: An Efficient SMT Solver", TACAS 2008. Y. Ge
  and L. de Moura, "Complete Instantiation for Quantified Formulas in Satisfiability Modulo
  Theories", CAV 2009, describe MBQI, which the Houdini rounds turn off and the CTI stage turns
  on.
