# The theory of rdra-ish's verification

This directory states what rdra-ish's verification tools decide, under which assumptions,
and on what evidence, for a reader trained in formal methods. Each document defines its
terms before it uses them, states its guarantees as propositions, and says for each one
whether it rests on a proof, a mechanical check, a differential test, or an assumption.

The documents describe the code at commit `b83b9544ccdef3701bf90383cd56d10ea2297787`
(origin/main, 2026-11-28). They cite code by symbol (`crate/src/path.rs::function`), never by
line. A document that is brought up to date with a later commit says so in its first
paragraph.

## Conclusion

<!-- derived-from ./tlc-agreement.md#residual-risk -->

Across the four theme documents, two residual risks outweigh the rest. They are the first two
items of [tlc-agreement.md, "Residual risk"](./tlc-agreement.md#residual-risk), and the other
three documents arrive at them from their own side.

1. **Common-mode faults.** The builder, which claim [I1](./claims.md#0-the-build) says returns
   `T_β(M)` of semantics.md, the choice of a cone, the staging of a
   property cone's runs, the quotient tables of a reduced cone, and the names that map native
   states to TLA+ ones (`TlaNames`) are read by both engines, so a fault in any of them moves
   the native verifier and TLC alike and agreement with TLC cannot show it. P40 and P54 (a
   value the build wraps) and P32 (an entity cone that leaves a raised mark out) are faults of
   this kind; P43 is a fault of the prover's encoding at bounds past the run's, which no
   comparison with TLC reaches. Only hand-written expectations, such as the engine corpus's
   `expect` lines, see these, and only on the models they name.
2. **No run-time defence against a wrong `ok`.** A printed counterexample is checked before it
   prints in some cases ([native.md](./native.md#counterexamples-what-is-checked-before-printing));
   an `ok`, and a `proved`, are never checked at run time. P50 and P54 give a wrong `ok`, P32 a
   missing finding, and P43 a `proved` that reaches too far, each with nothing in the run that
   notices.

Planned mitigation: P26, an independent check path for the builder (lane L6, branch
`fix/p26-reference-interpreter`; in progress). It is the first evidence for claim I1 that does
not read the build's output.

## Open problems

Each item is a stated guarantee the code does not give, a disagreement between documents
that bears on what a verdict means, or a gap in the evidence for a claim. Nothing here has
been weakened in the code or the notes; the owner decides which become issues. The
[claims inventory](./claims.md) refers to these by number.

Kinds: **guarantee** (a verdict can mean less than the tools or notes say), **evidence** (the
claim may hold, but its evidence is weaker than stated), **prose** (a note or code comment
disagrees with the code, with no effect on a verdict). Two items show a wrong `ok` of
`T_β(M)`, both reproduced: P54, at one instance, where a value past a byte wraps when the
build encodes it (a nullable Int column at `m = 255`, or a nullable Enum of 256 values), and
P50, at bounds no sample uses, where the packing of a state past 65,535 bits merged states
([native.md](./native.md#the-state-store-and-its-encoding); fixed in #479). P40 is the nullable-Int case of
P54, found independently for z3: it shows an `ok` and a `proved` that are wrong with respect
to the model text, because at `--int-range-max 255` the build itself departed from the model text (a failure of claim I1). P55 is a
third fixed-width fault of the same family, read only (fixed in #479). P43 shows a `proved` whose printed
reach ("any Int value") is wrong, because a larger `--int-range-max` gives a counterexample.
P32 shows that an entity cone can fail to report a deadlock, a state with no witness, or a use
case that never runs. P30 could give a wrong verdict if a model reached it. P51 and P56 are of
another sort: both engines agree, but the `ok` they print is not one that D17 or D20 of
[semantics.md](./semantics.md), as written, licenses. P1, P3, P4, P20, P30, P32, P40, P43, P50,
P51, P54, P55, and P56 are the items that bear on what a printed verdict means. This list is
what has been found, not a bound on what exists.

Numbering: P1 to P21 come from the survey for the claims inventory. Each theme document numbers
its items in a block of its own: theme (a) ([cones.md](./cones.md)) from P30, theme (b)
([z3.md](./z3.md)) from P40, theme (c) ([native.md](./native.md)) from P50, and theme (d)
([tlc-agreement.md](./tlc-agreement.md)) from P22 to P29, of which it uses P22 to P24 and P26.
P26 is the independent check of the builder (claim I1 of the claims inventory). P60 and
later come from the owner's review of [semantics.md](./semantics.md). Each theme's items
stay in one block.
